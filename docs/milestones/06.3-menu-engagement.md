# Milestone 06.3 — Menu-driven engagement interface

## Goal

A reusable menu-driven engagement handler that can be attached to any engageable object. The handler renders a tidy line-drawing menu, dispatches into submenus for the available features, and is configured per-object so the same code drives both a single-feature kiosk (e.g. a board-only terminal) and a full-service workstation (mail + boards + files all on one machine).

The existing raw command-line `TerminalHandler` (M5.7 + M6) stays as-is — it remains the "expert" interface and the substrate that the menu handler dispatches to under the hood. The menu is a different *kind* of engagement, not a replacement.

## Dependencies

- M5.7 (engagement primitive + per-kind handler registry).
- M6 (mail/boards/files services).
- M6.2 (file areas — the Files submenu lists areas).

## Scope

### A new engagement kind

```go
// internal/world/engage
const KindMenuTerminal = "menu_terminal"
```

Object policy at `objects.kind = 'item'` rows whose `object_engage.kind = 'menu_terminal'` opens the menu handler instead of the raw terminal. The choice is per-object, set via `wintermute.object.set_engage({slug=..., kind="menu_terminal", menu={...}})` from admin Lua.

### Per-object menu configuration

The `menu` field is an array of menu entries declaring which features this object exposes:

```lua
wintermute.object.set_engage({
  slug = "lobby-terminal",
  kind = "menu_terminal",
  menu = {
    { feature = "mail" },
    { feature = "boards" },
    { feature = "files", area = "dropbox" },
  },
})
```

Stored in `object_engage.policy` (already JSON-typed, M5.7) under a new top-level key. The set of supported `feature` values in M6.3:

- `"mail"`
- `"boards"`
- `"files"` (requires `area`)

A kiosk that only does mail simply lists one entry. An object can repeat a feature with different parameters (e.g. one "files" entry per area).

### Rendering

The menu uses Unicode box-drawing characters (`┌─┐│└┘├┤┬┴┼`) for a tidy look on ANSI/UTF-8 terminals and falls back to ASCII (`+`, `-`, `|`) when the engaged session's negotiated encoding is non-UTF-8 (the M1 capability layer already tells us which). Width follows the session's NAWS-reported width, capped at a sensible max (e.g. 80).

Example main-menu render:

```
┌────────────────── lobby terminal ───────────────────┐
│                                                     │
│   1)  Mail                  (3 unread)              │
│   2)  Message Boards                                │
│   3)  Files — Dropbox                               │
│                                                     │
│   Q)  Quit                                          │
│                                                     │
└─────────────────────────────────────────────────────┘
Select: _
```

Input is a single character (or short slug) followed by Enter; the handler also accepts the digit/letter alone for instant dispatch. `Q` (or `disengage`) closes the engagement; back-arrow `B` (or `..` / `back`) returns to the parent menu inside a submenu.

### Submenus

Each feature's submenu is a thin shell over the M6 services, presenting a list with numeric selectors and the same line-drawing chrome:

- **Mail submenu**: inbox listing with selectors → `Read`, `Reply`, `Delete`, `Compose new` actions. Compose uses the same paste-mode helper M6 introduced.
- **Boards submenu**: list visible boards → pick one → thread listing → pick one → thread view with `Reply` / `New post` / `Catch up`.
- **Files submenu** (per area): list of files in the area → `Download` issues a token and prints the URL; `Upload` issues an upload token and prints the URL + example curl line.

All submenus reuse the underlying `*mail.Service`, `*boards.Service`, `*files.Service` directly — the menu code is presentation only.

### Composing in menus

Subject prompts read a single line; body uses the same `.`-terminated paste mode as M6's command interface (`/abort` to cancel). The menu chrome is suppressed during paste mode and restored on commit/cancel.

## Out of scope

- Mouse / cursor positioning ANSI choreography. The menu is a sequence of `^L`-cleared frames, not a TUI.
- A separate admin menu — that's M6.4.
- Per-user menu customisation. Object configuration is operator-driven only.
- Player-tier scripting of menu entries (M8 hands player scripts a much more constrained API).

## Architecture

### Packages

- `internal/world/engage/menu/` — the new handler and renderer. Keeps the rendering helpers (box draw, ASCII fallback, page layout) isolated so they can be tested without spinning a session.
- `internal/world/engage/menu/feature/` — one small file per feature shim (`mail.go`, `boards.go`, `files.go`) that owns the submenu state machine. The shim depends on the service interface (not the engagement type), so submenus are testable in isolation against the services.

### Handler shape

```go
type Handler struct {
    host      *engage.Host
    close     func()
    deps      *engage.TerminalDeps  // reuse the M6 wiring
    menuSpec  []MenuEntry           // parsed from object_engage.policy
    state     menuState             // current frame: main, mail, boards/{slug}, files/{area}, compose
}
```

`menuState` is a tagged union (interface + small types per page). Every input line is dispatched to `state.handle(line, deps)`, which returns the next state and any output to write. Transitions clear the screen and re-render.

### Policy schema

Extend the existing `object_engage.policy` JSON with a new optional key:

```json
{
  "menu": [
    {"feature": "mail"},
    {"feature": "boards"},
    {"feature": "files", "area": "dropbox"}
  ]
}
```

A non-`menu_terminal` kind ignores the field. The admin Lua surface validates the entries on `set_engage`.

## Implementation tasks

1. Add `KindMenuTerminal` constant and policy parsing in `internal/world/engage`.
2. Implement the renderer in `internal/world/engage/menu/render.go` with both Unicode and ASCII variants.
3. Implement `Handler` and the menu state machine.
4. Implement the three feature submenus.
5. Extend `wintermute.object.set_engage` (worldapi) to accept and store `menu` entries.
6. Update `cmd/wintermute/main.go` to construct a menu handler when `host.Kind == KindMenuTerminal`.
7. Unit tests for the renderer (deterministic snapshots).
8. Unit tests for each feature submenu against the existing services.
9. An integration scenario in `internal/integration` that seats a player at a menu terminal, navigates to mail, sends a message, returns to the main menu, disengages.

## Acceptance criteria

1. An admin script can declare a menu terminal whose menu is `[mail]` only; that object opens to a single-option main menu.
2. The same script can declare a second terminal with the full `[mail, boards, files@dropbox]` set; the menu reflects all three.
3. A player engages a menu terminal, navigates to **Mail → Compose**, sends a message via paste mode, returns to the main menu, and disengages — all without using a raw command.
4. The rendered menu uses Unicode box-drawing characters when the session is UTF-8 and falls back to ASCII chrome on non-UTF-8 sessions, with no broken-glyph output.
5. Unread counts shown on the main menu are accurate at render time (e.g. `Mail (3 unread)`).
6. `make lint check-headers test` is green.

## Risks & open questions

- **Two engagement kinds in parallel**: keeping both the raw `terminal` handler and `menu_terminal` adds a small amount of duplication. Both share the same `TerminalDeps`, so the divergence is just the input/render loop. Worthwhile for the flexibility.
- **Pagination**: long inboxes/threads need paging. M6.3 ships fixed-window pagination (e.g. 15 entries per page with `N`/`P` for next/prev). More elaborate scrolling (PgUp/PgDn handling) is deferred.
- **Width detection on disconnect-reconnect**: when NAWS arrives late, the first frame may be drawn at the fallback width. Re-render on the next user input. Acceptable.
- **Localisation**: chrome strings are English-only. No i18n plumbing in M6.3.
