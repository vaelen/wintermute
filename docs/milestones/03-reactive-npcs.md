# Milestone 03 — Reactive NPCs

## Goal

A player can speak to an NPC in a room and get a response generated by a local Ollama model. NPCs have configurable personae. The `LLM` interface is pluggable from day one — adding Anthropic or OpenAI later requires only registering a new factory in `internal/llm/<name>`, with no changes to NPC code, world code, or persisted NPC config.

## Dependencies

- M2 (world layer): rooms, objects, broadcast.

## Scope

- `internal/llm` package: `LLM` interface, backend registry, factory pattern, message types, tool definition types (the tool surface is shaped but unused in M3).
- `internal/llm/ollama` package implementing `LLM` against `github.com/ollama/ollama/api`. Registers itself in `init()` under the name `"ollama"`.
- `internal/llm/fake` package (build tag `test`): deterministic backend used by unit tests.
- NPC entity: extends the `objects` table from M2 (kind = `'npc'`) with an `npc_config` row keyed by `object_id`.
- A simple addressed-only conversation loop: NPCs respond when (a) a player `say`s in their room AND (b) either the NPC's name appears in the message OR the NPC is the only other entity in the room.
- Per-NPC serialization (a `sync.Mutex` per NPC) so two players can't trigger overlapping LLM calls.
- A seed NPC ("the bartender") added to the seed world.
- Room rendering lists NPCs in the room (alongside players in the "Also here:" line) so players can see who they can address.

## Out of scope

- Long-term memory or summarization (M4).
- Tool calls (NPCs invoking world API functions) — the type signatures exist but tools aren't passed to the LLM yet. Tool invocation lands in M7 after admin scripting (M5) registers them.
- Autonomous behavior, scheduled goals, event bus (M7).
- Budgets (M7).
- Hosted LLM providers (deferred indefinitely; design ensures they slot in without surgery).

## Architecture

### `internal/llm` interface and registry

```go
// internal/llm/llm.go
package llm

type Role string
const (
    RoleSystem    Role = "system"
    RoleUser      Role = "user"
    RoleAssistant Role = "assistant"
    RoleTool      Role = "tool"
)

type Message struct {
    Role    Role
    Content string
    // Tool-call metadata fields. Unused in M3 but defined now so the type is stable.
    Name      string                 // for tool messages: tool name
    ToolCalls []ToolCall             // for assistant messages
    ToolCallID string                // for tool result messages
}

type ToolCall struct {
    ID        string
    Name      string
    Arguments map[string]any
}

type ToolDef struct {
    Name        string
    Description string
    Schema      map[string]any   // JSON schema for arguments
}

type ChatOpts struct {
    Model       string
    Temperature float32
    MaxTokens   int
}

type Response struct {
    Content    string
    ToolCalls  []ToolCall
    UsageIn    int
    UsageOut   int
}

type LLM interface {
    Chat(ctx context.Context, msgs []Message, tools []ToolDef, opts ChatOpts) (Response, error)
    Embed(ctx context.Context, text string) ([]float32, error)
}
```

```go
// internal/llm/registry.go
package llm

type Factory func(opts map[string]any) (LLM, error)

var registry = map[string]Factory{}

func Register(name string, f Factory)    // panics on duplicate
func Open(backend string, opts map[string]any) (LLM, error)
func Backends() []string                  // for debug/admin commands
```

### NPC layer

```go
// internal/npc/npc.go
type NPC struct {
    ObjectID   world.ObjectID
    Persona    string             // system prompt
    Backend    string             // e.g. "ollama"
    BackendOpts map[string]any
    Model      string             // chat model (overrides backend default if set)
    GateModel  string             // unused in M3, populated for M7
    MaxContext int
    llm        llm.LLM            // built once at load
    mu         sync.Mutex         // serializes Chat calls
}

func Load(ctx, db, world) (*Registry, error)
func (r *Registry) Get(id world.ObjectID) *NPC
func (r *Registry) HandleSay(ctx, room, speaker, text string)  // entry point from world
```

### Wiring `say` to NPCs

- The M2 `World.Say` is augmented: after broadcasting, it consults the NPC registry for NPCs in the room. For each NPC matching the addressing rules, it dispatches an LLM call in a goroutine (rate-limited by the NPC's mutex). The result is broadcast back to the room as `<npc> says, "<text>"`.
- The dispatch goroutine respects the session's context for cancellation — but does *not* block the speaker's session. The speaker sees their own message echoed; the NPC's reply arrives asynchronously.

### Addressing rules

An NPC responds to a `say` event when:
1. The speaker is in the same room, AND
2. (a) The NPC's name (case-insensitive, whole word) appears in the message text, OR
   (b) The NPC is the only non-speaker entity in the room (a "private" conversation).

These rules are intentionally restrictive — the autonomous loop (M7) handles the harder cases (initiation, ambient observation).

## Implementation tasks

1. Create `internal/llm` package with the types above. No backends yet.
2. Create `internal/llm/ollama` package. Import in `cmd/wintermute/main.go` for the side-effect registration.
3. Create `internal/llm/fake` package under the `test` build tag.
4. Add migration `0004_npc.sql` and `0005_seed_npc.sql`.
5. Create `internal/npc` package: `NPC`, `Registry`, `Load`, `HandleSay`.
6. Wire `npc.Registry.HandleSay` into `world.Say` (or a callback exposed by `world` to avoid a hard dependency from `world` on `npc`).
7. Implement the addressing rules.
8. Add a config section for default LLM options, e.g. `[llm.default]` from `plan.md`. The NPC's `backend_opts` are merged on top of the defaults.
9. Build the LLM client per-NPC at registry load (or lazily on first use, caching the result).
10. Add a small admin command, e.g. `@npcreload`, that re-reads `npc_config` rows and rebuilds clients (admin only; uses the existing `access_level`). This is the only command introduced in M3 beyond what M2 has.
11. Unit tests:
    - Registry registration / duplicate panic.
    - Addressing rules truth-table.
    - `HandleSay` with the fake backend produces the expected response shape.
12. Integration test: scenario test using the fake backend; one player says "hi, bartender" in the lobby, asserts the NPC's response is broadcast within a deadline.
13. Manual smoke test: with a real Ollama running locally and a small model pulled (`ollama pull llama3.2:3b`), interact with the bartender via telnet.

## Testing

- `go test -tags test ./...` for unit + scenario tests using the fake backend.
- `go test -tags 'test ollama' ./...` runs additional smoke tests that hit a local Ollama (skip if `OLLAMA_URL` is unset).
- Manual: `telnet localhost 2323`, log in, `say hi bartender`, observe a reply within a few seconds.

## Acceptance criteria

1. Compiling and running the engine with only `internal/llm/ollama` imported yields exactly one registered backend named `"ollama"`. `Open("ollama", opts)` succeeds; `Open("anthropic", opts)` returns a clear error.
2. The bartender NPC responds to `say hi bartender` in the lobby with text generated by Ollama.
3. The same NPC does **not** respond when a player talks to someone else by name in the same room and the bartender's name isn't mentioned.
4. Two players can both `say hi bartender` in quick succession; replies arrive in order without races and without crashing.
5. A bug in the LLM client (e.g. Ollama unreachable) does not crash the session — the NPC silently fails to respond and the error is logged with `slog`.
6. The NPC config can be updated via SQL + `@npcreload` and the new persona is reflected on the next interaction.
7. Switching the backend column on an NPC from `"ollama"` to a hypothetical future `"anthropic"` would require *only* registering that factory — no NPC, world, or schema changes.

## Risks & open questions

- **Ollama tool-calling**: format varies by model. M3 ships `tools` plumbed through but unused; M7 will validate against the chosen model family.
- **Backpressure**: with the per-NPC mutex, a slow Ollama call serializes interaction with that NPC. Acceptable for M3; M7's debounce will smooth this out.
- **Context length**: M3 doesn't manage context aggressively — only the rolling short-window of recent messages (≈10 turns) plus persona. The full memory architecture lands in M4.
- **Embedding model availability**: the embedding model isn't used in M3 but is configured. Don't fail startup if `nomic-embed-text` isn't pulled — defer the check until M4.
- **Speaker name in NPC context**: include the speaker's display name in the user message ("Player Foo says: ...") so the model knows who it's talking to. Decide the exact phrasing in this milestone and lock it.
