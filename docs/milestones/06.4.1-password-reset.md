# Milestone 06.4.1 — Password reset via admin

## Goal

Add a "Reset password" action to the Users section of the M6.4 admin menu: an admin issues a one-time password to a user; the user redeems it at login and is forced to choose a new password before doing anything else. Tokens are four common English words pulled at random from an embedded word list, valid for 48 hours, single-use.

## Dependencies

- M6.4 (admin menu skeleton — Users section already has list/view/promote/demote).
- M6 mail flow (`mail.SendFromSystem` for the audit notification).

## Scope

### Token shape

- Four words from an embedded word list (EFF "long" list, 7776 words, CC-BY 3.0 US — attribution is carried in the wordlist file itself). 4 words × ~12.9 bits ≈ 51 bits of entropy — adequate for a 48-hour single-use credential.
- Words joined with hyphens for unambiguous voice/chat relay: `correct-horse-battery-staple`. Case-insensitive on redemption.
- Selection uses `crypto/rand`. The word list is embedded into the binary via `//go:embed`; no runtime file dependency.

### Storage

Two new columns on `accounts`:

```sql
ALTER TABLE accounts ADD COLUMN reset_hash TEXT;
ALTER TABLE accounts ADD COLUMN reset_expires_at INTEGER;
```

`reset_hash` is the argon2id-encoded hash of the plaintext token (same format as `password_hash`). `reset_expires_at` is unix seconds. Both are NULL when no reset is outstanding.

Issuing a new reset for an account overwrites any prior `reset_hash` and `reset_expires_at` — at most one outstanding reset per account.

### Issuing a reset

`auth.Store.IssueReset(ctx, accountID int64, ttl time.Duration) (plaintext string, err error)`:

- Generates a four-word token via `crypto/rand`.
- Hashes it with argon2id and writes `reset_hash` and `reset_expires_at = now + ttl`.
- Returns the plaintext to the caller exactly once.

The admin menu calls this with `ttl = 48 * time.Hour`. The plaintext is shown to the admin on screen. The target user receives a `mail.SendFromSystem` message — subject `Password reset by <admin>`, body explains what happened **without** including the token. A structured slog line records `actor=<admin>`, `action=password_reset_issued`, `target=<username>`.

### Redeeming a reset (login flow)

`auth.Store.Login` after this milestone returns an extra "must change password" signal:

- Look up the account row (single read of `password_hash`, `reset_hash`, `reset_expires_at`).
- Try `password_hash` first. On match: return account, `mustChange = false`.
- On password mismatch: if `reset_hash` is non-null, not expired, and matches the (case-insensitive, hyphen-normalised) input, return account with `mustChange = true`. Do **not** clear `reset_hash`/`reset_expires_at` yet — they clear after the password change succeeds.
- All-paths failure returns `ErrInvalidCredentials`. The constant-time `verifyPassword` against the dummy hash on the unknown-user path continues to apply.

### Forced password change UX

A minimal engagement runs before the main menu is delivered when `mustChange` is set:

- Prompts twice for a new password.
- Validates length against `auth.minPasswordLen`.
- Requires the two entries to match.
- On success: updates `password_hash`, clears `reset_hash` and `reset_expires_at`, releases the session into normal flow. Emits slog `action=password_reset_redeemed` with `actor=<username>` (no admin attribution at redemption time — the issuance event already captured that).

If the user disconnects before completing the change, `reset_hash` stays intact and they can retry on next login until the original `reset_expires_at`.

### Active sessions

If the user has live sessions when the reset is issued, those sessions continue undisturbed. The reset only takes effect at the next `Login`. Forcibly terminating active sessions is out of scope.

## Out of scope

- Self-service "forgot password" (no in-game way to trigger when not logged in).
- Multi-factor authentication.
- Forcibly disconnecting active sessions on reset.
- Per-account or per-admin TTL configuration. 48h is hardcoded.
- Replacing M6's existing file-token format with the word-list format.

## Architecture

- `internal/auth/wordlist.txt` — EFF long list, CC0; embedded via `//go:embed`.
- `internal/auth/reset.go` — token generation, `IssueReset`, normalisation/matching helpers.
- `internal/store/migrations/0019_account_password_reset.sql` — adds the two columns.
- `auth.Store.Login` signature change to carry the must-change flag. Two reasonable shapes — either a new return value or a `LoginResult` struct. Picked during implementation; the signature change ripples through every call site, so the cleaner of the two wins even if it touches more files.
- `internal/world/engage/menu/feature_admin.go` — Users section gains a "Reset password" action that calls `IssueReset`, shows the plaintext to the admin, and dispatches the notification mail.
- The forced-password-change engagement: location decided at implementation time once the existing session-bootstrap flow is mapped. Likely sits next to the login engagement, before the main-menu hand-off.

10. Integration test: admin issues reset → user logs in with token → forced password change → can log in normally afterwards. The original token no longer works.
11. Integration test: expired token fails login.
12. Integration test: reissuing a reset invalidates the prior token.
13. Integration test: an admin cannot issue a reset for themselves (mirrors the self-promote/demote rule from M6.4).

## Acceptance criteria

1. An admin can issue a password reset for any other account from the admin menu and sees the four-word token displayed once.
2. The target user receives a `mail.SendFromSystem` notification that does **not** contain the token.
3. The user can log in with the token within 48 hours; on success, the session forces a password change before any other interaction.
4. After a successful password change, the original token no longer works and the new password works.
5. An expired token, a redeemed token, or one superseded by reissue all return `ErrInvalidCredentials`.
6. An admin attempting to issue a reset against their own account is refused at the menu.
7. `make lint check-headers test` is green.

## Risks & open questions

- **Word-list licensing**: EFF's long word list is CC-BY 3.0 US (the EFF site reports CC-BY for site content; no explicit CC0 dedication). Embed with the EFF attribution preserved at the top of `wordlist.txt` (Joseph Bonneau / EFF, 2016, https://www.eff.org/dice). No new Go dependency. Attribution-only is compatible with the MIT engine licence — downstream redistributors simply carry the wordlist header along with the file.
- **`auth.Login` signature change**: extending the return shape ripples through every caller. Worth getting right rather than wrapping in a backwards-compat shim — see CLAUDE.md.
- **Session bootstrap hook point**: the must-change flag has to gate user input *before* the main menu engagement starts. The exact wiring depends on what M6.3/M6.4 leave behind; verified at implementation time.
- **No active-session invalidation**: documented out of scope. Revisit if the threat model changes.
- **Token entropy vs. ergonomics**: 51 bits is below the 128-bit floor we use for password hashing, but it's a 48-hour single-use credential, not a long-term secret. Acceptable trade for human relayability.
