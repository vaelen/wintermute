# Milestone 06.2 — Admin Lua APIs for files, default Dropbox, upload notifications

## Goal

Expose the M6 files subsystem to admin-Lua, deliver upload-completion notifications to the file's owner as private mail (covering the M6 "persisted for next login" semantic without needing a new persistence channel), seed a default `Dropbox` file area so the menu UI in M6.3 has something to point at on a fresh install, and add the `@cleanup-files` in-game admin command (the only new admin command in this milestone — broader admin tooling lands later).

## Dependencies

- M6 (files service + HTTPS handler exist).
- M6.1 (mail admin API surface; we reuse `mail.Service.SendFromSystem`).

## Scope

### File areas (data model)

Introduce a lightweight area concept so the menu in M6.3 can present "Dropbox" as a distinct surface. Smallest workable shape: an `area TEXT NOT NULL DEFAULT 'dropbox'` column on `files`, plus a new table `file_areas` listing the human-displayable areas:

```sql
-- migrations/0016_file_areas.sql
ALTER TABLE files ADD COLUMN area TEXT NOT NULL DEFAULT 'dropbox';

CREATE TABLE file_areas (
    slug         TEXT PRIMARY KEY,
    name         TEXT NOT NULL,
    description  TEXT NOT NULL DEFAULT '',
    read_min_level   INTEGER NOT NULL DEFAULT 1,
    write_min_level  INTEGER NOT NULL DEFAULT 1,
    admin_min_level  INTEGER NOT NULL DEFAULT 3
);

INSERT INTO file_areas(slug, name, description)
    VALUES ('dropbox', 'Dropbox', 'Files shared by anyone, visible to anyone.');

CREATE INDEX idx_files_area ON files(area);
```

`files.Service.NewFile` gains an optional `Area string` parameter (default `"dropbox"`). `ListByOwner`, `GetFile`, and the upload HTTP path stamp the area onto created rows. ACL semantics mirror M6 boards' min-level bands.

### `wintermute.file.*` (admin-Lua)

- `wintermute.file.area.create({ slug, name, description?, read_min_level?, write_min_level?, admin_min_level? })`
- `wintermute.file.area.delete(slug)` — refuses if any files reference it.
- `wintermute.file.area.list()` → array of area tables.
- `wintermute.file.list({ owner_username?, area? })` → array of file rows.
- `wintermute.file.delete(slug)` — removes the file row; the janitor reaps the blob.
- `wintermute.file.set_acls(file_slug, { account_username, perms })` — wraps `file_acls`. (Not currently used by anything; lays the groundwork for per-file shares.)

### `@cleanup-files` admin command

In-game `@`-command (registered via `worldcmd.AdminBackend`) that calls `files.Service.Janitor(ctx, grace)` synchronously and reports `"reaped N expired token(s), M orphan blob(s)"` to the invoker. Gated by `AccessAdmin`.

### Upload-complete notifications via system mail

Replace the M6 `OnUpload` callback that currently only logs:

1. Look up the file's owner.
2. Call `mail.Service.SendFromSystem(ctx, ownerUsername, "Upload complete: <slug>", body)` where `body` includes the slug, byte size (human-readable), mime, and the in-world download command.
3. The mail row carries `from_id = NULL`, `from_name = "<system>"`. The recipient sees it in their inbox immediately (live session) or on next login (post-MOTD unread count + first `mail` from a terminal).

This satisfies the M6 acceptance criterion "Uploads that finish after the player has disconnected are persisted and visible on next login" by piggybacking on mail rather than introducing a new persistent-notifications table.

## Out of scope

- A live-session "[terminal] Upload received: …" *push* — that would need a session-by-account registry that doesn't exist yet, and the mail-based delivery covers the persistence requirement on its own. If/when a push channel is built, it's additive.
- Player-facing commands to manage areas or share files. That's the menu UI in M6.3.
- File quotas. (Worth doing eventually; not blocking.)

## Implementation tasks

1. Add migration 0016: `files.area` column + `file_areas` table + seed `dropbox`.
2. Extend `files.Service.NewFile` (and the HTTP upload path) with the area parameter.
3. Add `files.Service.GetArea`, `ListAreas`, `CreateArea`, `DeleteArea`.
4. Add `worldapi` bindings under `wintermute.file.*` and register in the Lua VM pool.
5. Wire `@cleanup-files` into `worldcmd.AdminBackend`.
6. Replace the `OnUpload` callback in `cmd/wintermute/main.go` to deliver via `mail.SendFromSystem`.
7. Unit tests for the new service methods, the area FK behaviour, and the upload→mail flow (using httptest as in M6).
8. Update `wintermute.example.toml` to mention the default `dropbox` area.

## Acceptance criteria

1. A fresh install has exactly one `file_areas` row: `dropbox`.
2. Uploading via the HTTPS endpoint creates a `files` row with `area = 'dropbox'` and the file's owner gets a system mail titled `Upload complete: <slug>` containing the size and mime.
3. The owner sees the unread count on next login if they were offline when the upload completed.
4. An admin running `@cleanup-files` after expiring tokens get reaped sees a count line and the rows are gone.
5. An admin Lua script can create a second area, upload a file into it (via `wintermute.file.list({area="…"})` filtering), and delete the area when empty (and not delete it when non-empty).
6. `make lint check-headers test` is green.

## Risks & open questions

- **Area renaming**: not supported in M6.2. Renaming `dropbox` is a config-by-edit operation; the migration's seed runs once. If we ever rename, all references in mail bodies (e.g. "Upload complete in `dropbox`") would still point at the old name — acceptable.
- **File ACLs vs area ACLs**: the per-file `file_acls` table predates areas. M6.2 leaves both in place; M6.3's menu UI is expected to honour `file_acls` overrides on top of `file_areas.read_min_level`.
- **Notification spam**: an admin uploading 50 files in a row gets 50 mails. Reasonable tradeoff; if it bites, batch in a follow-up.
