# Milestone 06.4 — Menu-driven admin interface

## Goal

An admin-tier extension to the M6.3 menu engagement: an "Admin" entry that appears in the main menu when the engaged player is an admin and the object's policy opts in. The admin menu drives system configuration and database management — users, mail, boards, files, objects, rooms, FTN networks, system MOTD. Operators can choose which terminals expose the admin entry (some are public, some are admin-only).

## Dependencies

- M6.3 (menu engagement framework + the feature shim pattern).
- M6.1 + M6.2 (the Lua admin APIs the menus delegate to under the hood).

## Scope

### Policy opt-in

Add `"admin"` as a recognised feature in the M6.3 menu policy:

```json
{
  "menu": [
    {"feature": "mail"},
    {"feature": "boards"},
    {"feature": "files", "area": "dropbox"},
    {"feature": "admin"}
  ]
}
```

A terminal that lists `admin` in its policy *and* whose current participant has `AccessLevel = admin` shows the entry. Players below admin tier never see it (the menu skips the entry rather than rendering a grayed-out row, so the menu numbering stays clean). The render path consults `acc.AccessLevel` on every frame; a level change mid-session takes effect on the next render.

### Admin submenu structure

The admin menu is itself a menu of menus. Initial top-level entries:

```
┌─────────────── admin console ────────────────┐
│  1)  Users                                   │
│  2)  Mail                                    │
│  3)  Boards                                  │
│  4)  Files                                   │
│  5)  Objects                                 │
│  6)  Rooms                                   │
│  7)  FTN networks                            │
│  8)  System                                  │
│                                              │
│  B)  Back     Q)  Quit                       │
└──────────────────────────────────────────────┘
```

Each subsection supports list + view + a small set of mutations. Specifically, M6.4 ships:

- **Users**: list (with access level + last login), view (terminal prefs, account meta), promote/demote between `player`/`builder`/`admin`, reset password (generates a one-shot reset token printed to the admin and mailed to the user via `mail.SendFromSystem`).
- **Mail**: list system-broadcast queue history, broadcast a new message (paste-mode compose), purge a specific message from a user's inbox.
- **Boards**: list, create (paste-mode for description), delete (empty boards only), set ACL bands, set area_tag.
- **Files**: list areas, create/delete areas, list files in an area, delete a file, run `@cleanup-files` from the menu.
- **Objects**: list (paginated by slug), view one (slug/name/kind/owner/permissions/engage policy), delete. Edit is out of scope here — keep that on admin Lua.
- **Rooms**: list, view (slug/name/description/owner/permissions, exits), set MOTD-style room properties. Edit-description gets paste-mode.
- **FTN networks**: list, view, set default (clear + set in one tx).
- **System**: view + edit MOTD, view server stats (uptime, accounts, sessions, mail/board/file counts).

Every mutation routes through the existing M6.1 / M6.2 admin Lua APIs or — where simpler — directly at the service layer (it's the same code, the menu is just a different caller).

### Audit logging

Every admin-menu mutation writes one structured `slog` line with `actor`, `action`, `target`, and any non-secret arguments. If a `world_log` SQLite table is in place by this milestone, mutations also append there.

## Out of scope

- A web admin UI.
- Bulk operations (e.g. "delete every file older than X"). One-at-a-time is fine in M6.4; scripting handles bulk.
- Live tailing of server logs from the menu. (Useful, but adds a streaming concern that the menu state machine doesn't currently model.)
- ACL editing beyond promote/demote — fine-grained per-object permissions stay in admin Lua.

## Architecture

- `internal/world/engage/menu/feature/admin.go` — new feature shim implementing the admin submenu state machine, mirroring how the M6.3 features are structured.
- Reuses M6.3's renderer and pagination helpers verbatim.
- Reuses M6.1/M6.2's service-layer methods for every mutation; no new persistence here.
- A small `internal/world/engage/menu/feature/admin/audit.go` writes the audit entries (slog + optional world_log).

## Implementation tasks

1. Extend M6.3 policy validation to accept `"admin"` as a feature value.
2. Update the M6.3 main-menu renderer to filter out admin-only entries when the current participant is not an admin.
3. Implement the admin submenu state machine and each subsection's render+dispatch.
4. Wire the audit log writes.
5. Unit tests per subsection.
6. Integration test that seats an admin at an admin-enabled terminal, performs one mutation in each subsection, asserts DB state and that the audit line was emitted.
7. Integration test that confirms a non-admin seated at the same object does *not* see the admin entry.

## Acceptance criteria

1. A terminal whose policy lists `"admin"` shows the entry to admins and hides it from non-admins, with menu numbering remaining contiguous in both cases.
2. From the admin menu an admin can: promote a player to builder, broadcast a system mail, create and delete an empty board, delete a file, view a room and an object, set the default FTN network, and edit the MOTD — and every action lands in the DB.
3. Every successful mutation emits a structured `slog` line with `actor`/`action`/`target`.
4. `make lint check-headers test` is green.

## Risks & open questions

- **Privilege escalation via demotion**: an admin demoting themselves out of admin would lock everyone else out if no other admin exists. The menu blocks self-demotion when `count(admin) == 1`.
- **Password reset**: the reset token mailed to the user is plaintext-equivalent. Treat as one-shot; expire in a short window. Generate via `crypto/rand` as the M6 file tokens do.
- **Long pages**: paginate every list submenu; never render more than a screen at once.
- **Concurrency**: two admins editing the same row at once. M6.4 reads-then-writes without optimistic locking; last-write-wins is acceptable at the scale this server runs at. Revisit if it becomes a real problem.
