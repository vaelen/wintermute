# Milestone 06.5 — ANSI-based terminal detection

## Goal

Detect terminal type and size from ANSI control sequences so that non-telnet clients (raw `nc`, web-based PTY bridges, TLS-only clients) get the same auto-configured experience as telnet clients. Telnet's TTYPE and NAWS subnegotiations remain the preferred sources when available; ANSI probes fill the gap when they aren't.

The detection flow lands in a single reusable helper called at login *and* by `terminal detect`. M6.3.1 already shipped `terminal detect` for the telnet path (re-poll TTYPE, refresh NAWS); this milestone gives the non-telnet path real detection rather than the current "coming soon" placeholder.

## Dependencies

- M1 (telnet conn + the existing login-time ANSI Device Attributes probe).
- M6.3.1 (Presence.TermType / TermWidth / TermHeight fields, engage.Resizer, `terminal detect` skeleton, `terminal` status output).

## Scope

### Pre-probe banner

Today the login flow writes `PRESS ENTER TO BEGIN.` and the ANSI DA probe (`CSI c`) in one go. The probe's response is a short CSI sequence (e.g. `CSI ? 1 ; 2 c`) that a non-ANSI terminal renders as visible garble. Add a `Detecting terminal type...\r\n` line *immediately before* the probe so the garble — when it happens — has obvious context.

```
WINTERMUTE

Detecting terminal type...
PRESS ENTER TO BEGIN.
```

### ANSI probes (in order)

The helper sends all probes back-to-back, then reads the user's first input line. Any control-sequence responses on that line are consumed before the rest is treated as user text. Each probe is independent — silence on one doesn't suppress the others.

1. **Primary Device Attributes** (`CSI c`) — already sent at login. Reply: `CSI ? <params> c`. Coarse VT class only; mostly useful as an "is this ANSI at all" gate.

2. **Secondary Device Attributes** (`CSI > c`). Reply: `CSI > <type> ; <version> ; <hardware> c`. Type codes are well-known: 0=VT100, 1=VT220, 41=xterm, 65=VT500, 77=mintty, 82=rxvt, 84=tmux, 85=rxvt-unicode. When the session is non-telnet (or telnet without TTYPE), the decoded `type` value seeds `TermType` ("xterm", "rxvt-unicode", "mintty", etc.).

3. **XTVERSION** (`CSI > 0 q`). Reply: DCS-wrapped name+version string ("xterm(384)", "WezTerm 20240814-114907-3b2eba32", "kitty 0.35.2", "tmux 3.4"). Modern terminals only; absence is not an error. When present it provides a better-than-Secondary-DA identifier and gets stored alongside the substring-derived `TermType`.

4. **Window size in cells** (`CSI 18 t`). Reply: `CSI 8 ; rows ; cols t`. xterm-family terminals support this; bare VT100 does not. When present and width/height are missing (no NAWS), these become the source of truth.

5. **Cursor-position fallback for size**: `CSI s` (save cursor), `CSI 999 ; 999 H` (clamp to bottom-right), `CSI 6 n` (Cursor Position Report), `CSI u` (restore). Reply to the CPR: `CSI <rows> ; <cols> R`. Universal across ANSI terminals — used when `CSI 18 t` produced no reply. The save/restore is mandatory so the user doesn't see the cursor jump.

The helper waits a short window (e.g. 200ms) for replies after writing the probes, then reads the user's input line. Any unread bytes from probe replies that arrive during the user-input read are still consumed by the same parser.

### Source-of-truth precedence

When multiple sources report the same axis, prefer the more reliable one:

- **TermType**: TTYPE (telnet) → XTVERSION → Secondary DA decode. First non-empty wins.
- **Width / Height**: NAWS (telnet) → `CSI 18 t` reply → `CSI 6 n` fallback. First positive value wins.

Probes that don't contradict an already-set source don't overwrite it — so a telnet client with both TTYPE and Secondary DA replies keeps the TTYPE value (which the user can re-poll via `terminal detect`).

### Factored helper, two entry points

```go
// internal/session/detect.go (proposed)
//
// runDetect emits the pre-probe banner, sends every applicable ANSI
// probe, optionally re-requests telnet TTYPE, waits briefly, and
// returns a populated DetectHints. Used at login and by the
// `terminal detect` command.
func (h *Handler) runDetect(s *Session) term.DetectHints
```

- **At login**: replaces the current inline DA-probe code. The "Detecting terminal type..." line precedes "PRESS ENTER TO BEGIN."; the press-enter read also drains probe replies.
- **From `terminal detect`**: drops the banner line into the running command-loop output, sends probes, reads replies on a short timeout (no press-enter step), reconfigures with the returned hints. Telnet support is *not* re-detected — that's a connection-level property that doesn't change after the first IAC byte.

The helper does not branch on `s.caps.Telnet` for the ANSI probes — they're sent unconditionally and silently ignored by terminals that don't understand them. It does branch for the TTYPE re-request (no-op outside telnet, already in M6.3.1's `Conn.RequestTTYPE`).

## Out of scope

- Mid-session window-resize tracking via probe polling. NAWS still covers that for telnet; non-telnet clients on a resized window need a manual `terminal detect`.
- Color-depth probing (`OSC 4 ; <i> ; ? BEL` to read palette entries). The existing `ANSI` and `Color` capability booleans are sufficient for M6.x rendering.
- True-color (24-bit) capability detection. Inferred from XTVERSION / `TermType` if at all.
- DECRQM (Request Mode) probes for individual features. Not needed by current rendering paths.

## Implementation tasks

1. Add a `Detecting terminal type...\r\n` write before the DA probe at login.
2. Extend the telnet/ANSI parser (in `internal/term`) to recognise Secondary DA, XTVERSION DCS, `CSI 18 t` reply, and `CSI 6 n` reply. Each writes into a new field on `term.DetectHints` (e.g. `SecondaryDAType`, `XTVersion`, `WinSize {rows,cols}`, `CursorPos {rows,cols}`).
3. Factor login-time detection into `Handler.runDetect(s) term.DetectHints` that handles: write banner, send probes, optionally re-request TTYPE (when `s.tc.Negotiated()`), wait, return hints. Login calls it; the press-enter read drains residual probe replies.
4. Update `term.AutoDetect` (or a sibling helper) to fold Secondary DA / XTVERSION into `TermType` and to fold `CSI 18 t` / CPR into Width/Height using the precedence rules above.
5. Rewrite `terminalDetect` (currently the M6.3.1 telnet-only path) to call `runDetect`. Remove the "Coming soon" branch; the same code now handles both transports.
6. Bookkeeping: ensure cursor-restore (`CSI u`) lands even if the user types fast enough to interleave their input with the CPR probe. Wrap the save/move/query/restore in a single write so the bytes travel together.
7. Tests:
   - Parser unit tests for each new response shape (Secondary DA, XTVERSION DCS, `CSI 8 ; r ; c t`, `CSI r ; c R`).
   - `term.AutoDetect` unit tests for the precedence rules (TTYPE wins over Secondary DA when both present; NAWS wins over `CSI 18 t`; `CSI 18 t` wins over CPR).
   - Integration test: raw-TCP (non-telnet) client that responds with `CSI > 41 ; 384 ; 0 c` and `CSI 8 ; 30 ; 100 t`, runs through login, then asserts `terminal` status shows xterm-family type and 100x30 size.
   - Integration test: telnet client that responds to nothing — exercises silence-tolerance.

## Acceptance criteria

1. A raw-TCP client (no telnet negotiation) that emulates an xterm-family response produces a non-empty `TermType` and a non-default `Width`/`Height` on the session.
2. A telnet client with TTYPE = "vt100" but Secondary DA = type-41 (xterm) keeps `TermType` == "vt100" — TTYPE wins.
3. A raw-TCP client that ignores `CSI 18 t` but responds to CPR gets `Width`/`Height` populated from the CPR fallback. The cursor returns to its pre-probe position (verified via DECSC/DECRC bracketing the probe).
4. `terminal detect` works identically on telnet and non-telnet sessions; both refresh `TermType` + `Width` + `Height` and trigger the existing `engage.Resizer` hook on the active engagement.
5. A user on a terminal that ignores every probe (e.g. an old VT100) sees the "Detecting terminal type..." line and no garble, lands at the encoding prompt, and proceeds normally. `terminal` status shows `type: (not reported)`.
6. `make lint check-headers test` is green.

## Risks & open questions

- **Garble on truly dumb terminals**: a terminal that doesn't strip CSI sequences and doesn't reply to them will show the probe bytes verbatim. The pre-probe banner mitigates this but doesn't eliminate it. Acceptable for M6.5; documented in the user-facing help text for `terminal detect`.
- **DCS response framing**: XTVERSION returns a DCS-wrapped string terminated by ST (`ESC \`) or BEL. The parser needs to handle both terminators and a stuck-open DCS (treat as ignored after a timeout).
- **CPR + user input race**: if the user hits Enter during the 200ms wait, their `\n` and the CPR reply may interleave. The save/move/query/restore must be atomic (one Write call) and the parser must consume CPR-shaped sequences out of the input stream regardless of where they land in the line buffer.
- **Probe noise in tests**: integration tests that don't emulate a probe-aware client must tolerate the new banner line. Existing `loginNew` already expects banner text by substring, but tests that match exact byte counts may need updating.
- **No persistence**: matching M6.3.1's `TermType` decision, detection results are per-session only. A re-detect on reconnect is automatic; a re-detect mid-session is `terminal detect`.
